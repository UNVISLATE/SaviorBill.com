Когда встает задача продавать цифровые товары, подписки или доступ к инфраструктуре, разработчик почти всегда оказывается перед не самым приятным выбором:

1. **Легаси-монстры 15-летней давности (WHMCS, BILLmanager, ClientExec):** огромные монолиты на PHP/Perl, спагетти-плагины с прямым доступом к базе данных, тяжелый интерфейс и постоянный риск уронить весь сервер из-за ошибки в одном стороннем модуле.
2. **Закрытые зарубежные SaaS (Stripe, Paddle, LemonSqueezy):** конские комиссии (5–10%), недоступность во многих юрисдикциях, отсутствие поддержки локальных платежек (СБП, ЮKassa, крипта) и полная зависимость от внешнего сервиса.
3. **Самописные боты «на коленке»:** работают до первой тысячи пользователей, после чего превращаются в хаос без учета, мультивалютности и централизованной аналитики.

Именно поэтому родился **SaviorBill** — современная, событийно-ориентированная self-hosted платформа с изолированной логикой на Lua и Server-Driven интерфейсом.

## Архитектурное разделение: Core vs Workers

Главная инженерная идея SaviorBill — **нулевой код интеграций в ядре биллинга**.

Ядро платформы (`BillingCore`) написано на **Python 3.12 + FastAPI + PostgreSQL 16**. Оно отвечает исключительно за финансовую целостность, мультивалютный баланс, транзакции, права доступа и учет пользователей. 

Вся внешняя деятельность — создание серверов, генерация VPN-конфигов, проверка платежей эквайрингов — вынесена в изолированный сервис **LuaWorker** (LuaJIT). Связь между ними происходит асинхронно через шину задач **Valkey Streams**.

```text
[Клиентский запрос]
       │
       ▼
 [BillingCore (FastAPI)] ──(Транзакции & Баланс)──► [PostgreSQL]
       │
       ▼ (Valkey Streams: задача с контрактом ctx)
 [LuaWorker (LuaJIT Sandbox)]
       │
       ├─► Запрос к внешнему API (WireGuard / Proxmox / ЮKassa)
       └─► Возврат: { public, private, state, expires_at }
```

Если внешний сервис зависнет, вернет 500 ошибку или упадет — ядро биллинга продолжит работать стабильно и штатно обработает ретрай.

## Контракты задач в Lua: строгость без лишней сложности

Каждый Lua-скрипт работает только с объектом `ctx` — изолированным контекстом своей задачи. Скрипту не нужно знать внутреннее устройство базы данных или таблиц.

![Встроенный редактор Lua-скриптов прямо в админке](/images/admin-lua.png)

### Пример: Скрипт выдачи VPN-подписки

```lua
-- scripts/services/wireguard.lua
function handle(ctx)
  if ctx.action == "create" then
    -- Генерация пира через внешнее API панели
    local login = ctx.user.login
    local peer_conf = api.wireguard:create_peer(login)

    return {
      public = {
        config = peer_conf,
        qr = peer_conf,
        instructions = "Импортируйте конфиг в приложение WireGuard."
      },
      private = {
        peer_id = login .. "_wg"
      },
      state = "active",
      expires_at = os.time() + (30 * 86400)
    }
  elseif ctx.action == "freeze" then
    -- Отключение пира при нехватке средств
    api.wireguard:disable_peer(ctx.user.login)
    return { state = "frozen" }
  end
end
```

Что здесь происходит:
* **`public`**: данные, которые автоматически передаются клиенту;
* **`private`**: внутренние идентификаторы, доступные только ядру;
* **`state`** и **`expires_at`**: параметры, по которым биллинг автоматически управляет жизненным циклом услуги.

## Server-Driven UI: sbuiSDK

В классических биллингах добавление нового типа услуги требует правок шаблонов фронтенда (Smarty, Blade, React). 

В SaviorBill используется концепция **Server-Driven UI (`sbuiSDK`)**: Lua-скрипт или манифест услуги сами описывают, как услуга должна отображаться у покупателя. 

![Витрина каталога и карточка товара в клиентском кабинете](/images/client-product.png)

Клиентский кабинет `SBPersonalAccountClient` парсит этот JSON и автоматически рендерит:
- Векторные QR-коды для быстрого импорта мобильными устройствами;
- Поля копирования токенов и ключей в 1 клик;
- Кастомные формы настроек и ползунки ресурсов;
- Инструкции в Markdown.

Фронтенд не нужно пересобирать — новый сервис готов к продаже сразу после сохранения Lua-манифеста в админ-панели.

## Каталог услуг и гибкие модели тарификации

В SaviorBill поддерживаются четыре фундаментальные модели продажи:
1. **`fixed`**: разовая покупка с фиксированной ценой;
2. **`custom`**: произвольная сумма в заданных пределах (пополнение балансов, донаты);
3. **`tiered`**: тарифная сетка с разбивкой по длительностям (месяц, квартал, год);
4. **`configurable`**: интерактивный конструктор ресурсов (vCPU, RAM, диск) с пересчетом стоимости в реальном времени.
